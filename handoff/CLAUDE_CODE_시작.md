# 🚀 클로드 코드 시작 가이드

> **이 문서를 어떻게 쓰나요?**
> 클로드 코드를 처음 실행하면, 작업할 폴더에 이 핸드오프 패키지(7개 파일)을 모두 넣어주세요.
> 그 다음 아래 **§A의 첫 메시지 프롬프트**를 그대로 복사해서 클로드 코드에 첫 메시지로 붙여넣으면 됩니다.

---

## A. 첫 메시지 (그대로 복사 → 붙여넣기)

```
이 폴더에 있는 한국 중·고교 학부모용 "고교선택 적성검사" 웹앱의 작업을 인계받아 진행할 거야.
이전 세션에서 완성된 v2 프로토타입과 모든 설계 결정·가중치 테이블이 정리된 핸드오프 패키지가 있어.

작업 시작 전에 반드시 다음 4개 파일을 이 순서로 정독해줘:

1. SPEC.md                — 마스터 스펙. 모든 설계 의사결정과 단어 정책
2. WEIGHTS.json           — 모든 가중치·임계값·멘탈 유형 정의 (기계 판독용)
3. QUESTIONS.json         — 39개 문항 + 8개 계열 (정확한 텍스트)
4. index.html             — 작동하는 참조 구현 (분쟁 시 이게 정답)

읽기를 마치면 다음 항목을 한 번에 답해줘:

- 6개 평가 축의 코드명과 각 축의 문항 수
- 7개 고교 유형 이름 (한국어 그대로)
- 멘탈 cap의 두 임계값과 각 임계값에서 적용되는 max 점수
- 계열 fit cap이 적용되는 3개 규칙
- 사용 금지 단어 6개 (학부모가 어려워하는 고교 전문용어)
- SPEC §10에 있는 11개 검증 시나리오 중 5번과 8번의 기대 1순위 학교

내가 이 답을 검수한 다음에야 코드 변경을 시작할 수 있어.

⚠️ 절대 원칙:
- QUESTIONS.json의 문항 텍스트는 한 글자도 수정 금지
- WEIGHTS.json의 모든 숫자값은 한 자리도 수정 금지 (요청이 있을 때만)
- "세특", "학종", "비교과", "교과/지역균형 전형" 같은 고교 전문용어 사용 금지
- 멘탈 약(N<50) → 특목고 추천 절대 금지 (cap 로직 빼지 말 것)
- 코드 변경 후에는 SPEC §10의 11개 시나리오로 회귀 테스트 필수

확인하면 다음 작업 지시를 줄게.
```

## B. 작업 지시 시 권장 패턴

새 기능을 추가하거나 변경할 때, 위 첫 메시지에 응답한 클로드 코드에게 다음 형식으로 지시하세요:

```
[작업 의뢰]
무엇을: <한 줄로 무엇을 바꿀지>
왜: <배경/목적>
영향 범위: <SPEC의 어느 섹션과 관련 있는지 클로드가 먼저 답해줘>

진행 순서:
1. SPEC.md의 관련 섹션을 읽고 영향 범위를 한 줄로 요약
2. 변경 전 vs 변경 후 차이를 표로 보여줘
3. 변경 후 SPEC §10의 11개 시나리오 모두 통과하는지 시뮬레이션
4. 통과하면 코드 변경
5. 변경 후 SPEC.md / QUESTIONS.json / WEIGHTS.json도 함께 업데이트 (필요 시)
```

## C. 자주 쓸 작업 예시 (그대로 가져다 써도 OK)

### 예시 1 — 가중치 미세 조정

```
[작업 의뢰]
무엇을: 외국어 계열만 선택했을 때 외고 1순위 점수가 너무 낮음
왜: 학부모 피드백 — "외국어 계열인데 외고가 자공고와 비슷하면 신뢰가 떨어진다"
영향 범위: 너가 먼저 분석해줘 (TRACK_TYPE_BONUS 또는 axis_bonus_multiplier 조정 후보)

진행 순서는 §B와 동일.
SPEC §10의 시나리오 6 ("외국어 단독 → 외고 91")이 기준점이야. 변경 후 외고 점수가 91 이상이 되어야 해.
```

### 예시 2 — 새 문항 추가

```
[작업 의뢰]
무엇을: 축 D(환경·생활·비용)에 통학 수단 관련 문항 1개 추가
왜: 현재 D는 통학시간만 묻고 수단(대중교통/도보/차량)을 안 물어봄
영향 범위: QUESTIONS.json + axis_type_weights는 그대로 (D축 문항 수만 5→6)

새 문항 ID는 D1-2 로 명명. 텍스트는 너가 초안 5개를 만들어주면 내가 고를게.

⚠️ 단어 정책: 초중등 학부모용 어휘만 사용. SPEC §7 참조.
```

### 예시 3 — UI 디자인 변경

```
[작업 의뢰]
무엇을: 결과 화면의 6각형 차트를 더 크게 + 모바일에서 색상 대비 강화
왜: 학부모 사용자 테스트에서 "숫자가 잘 안 보인다" 피드백 다수
영향 범위: index.html의 buildHexagonSVG 함수 + CSS

⚠️ 변경 전 데스크톱·모바일 모두 스크린샷 또는 미리보기로 확인.
스코어링 알고리즘은 절대 건드리지 마.
```

### 예시 4 — 클라우드 백엔드 확장

```
[작업 의뢰]
무엇을: Supabase에 응답자 그룹(반/학년) 필드 추가 + 그룹별 통계
왜: 한 학원에서 여러 반을 운영할 때 반별 비교가 필요
영향 범위: SUPABASE_설정.sql (테이블 스키마) + index.html (입력 폼/관리자 통계)

진행:
1. 새 SQL 마이그레이션 스크립트를 만들어줘 (기존 데이터 보존)
2. 응답 폼에 그룹 선택 필드 추가
3. 관리자 화면에 그룹 필터 + 그룹별 통계 카드
4. SUPABASE_설정가이드.md 업데이트
```

## D. 클로드 코드와 작업할 때 주의사항

1. **모든 응답이 끝나면 git diff로 확인**
   클로드 코드는 파일을 직접 수정합니다. 매 변경 후 `git diff` 또는 변경 내역을 본인 눈으로 검수하세요.

2. **회귀 테스트는 자동화**
   SPEC §10의 11개 시나리오를 노드 스크립트로 만들어 두면, 매 변경 후 1초 만에 회귀 검출 가능합니다. 첫 작업으로 이걸 만들어달라고 하세요:

   ```
   [작업 의뢰] SPEC §10의 11개 시나리오를 자동 검증하는 test.cjs 파일을 만들어줘.
   index.html에서 computeScores 함수를 추출해 직접 호출하고, 1순위 학교명과 점수가
   기대값과 일치하는지 비교. 실패 시 어느 시나리오가 어떻게 다른지 출력.
   ```

3. **WEIGHTS.json을 단일 진실 공급원으로**
   가능하면 가중치를 코드에 하드코딩하지 말고 WEIGHTS.json을 fetch해서 쓰는 구조로 리팩터링하세요. 그래야 비전문가도 수치만 조정해서 배포할 수 있어요.

   ```
   [작업 의뢰] index.html이 빌드 시 WEIGHTS.json을 inline 임베드하는 구조로 바꿔줘.
   가중치 변경은 WEIGHTS.json만 수정하면 끝나도록.
   ```

4. **Supabase 키는 .env로**
   현재 `SUPABASE_URL`/`SUPABASE_ANON_KEY`가 코드 인라인입니다. 클로드 코드 환경에서는 `.env` 파일과 빌드 스크립트로 주입하는 구조로 분리하세요.

5. **버전 표시**
   변경할 때마다 SPEC.md의 `spec_version` 을 v2 → v2.1, v2.2 등으로 올려주세요. JSON 파일도 동일.

## E. 문제 발생 시 복구

만약 어떤 변경이 회귀를 일으켰다면:

```
[복구 의뢰] 직전 변경으로 SPEC §10의 시나리오 N번이 깨졌어. 변경을 되돌리고
무엇이 잘못됐는지 분석해줘. 다시 시도하기 전에 영향 범위를 더 좁혀서 제안해줘.
```

핸드오프 패키지(이 폴더의 7개 파일)는 **검증된 v2 상태의 스냅샷**입니다. 어떤 변경도 결국 이 상태로 되돌릴 수 있어야 합니다. 폴더를 통째로 백업해 두세요.

## F. 권장 폴더 구조

클로드 코드 시작 시 다음과 같이 구성하면 깔끔합니다:

```
gokyo-test/
├── handoff/                      ← 이 핸드오프 패키지 통째로
│   ├── SPEC.md
│   ├── QUESTIONS.json
│   ├── WEIGHTS.json
│   ├── index.html                ← 참조 구현 (편집 금지)
│   ├── SUPABASE_설정.sql
│   ├── SUPABASE_설정가이드.md
│   ├── CLAUDE_CODE_시작.md       ← 이 파일
│   └── README.md
├── src/                          ← 새 구현 작업 폴더
│   └── (클로드 코드가 만들 파일들)
├── test/                         ← 회귀 테스트
│   └── scenarios.cjs
└── .gitignore
```

`handoff/` 폴더는 **읽기 전용 참고자료** 처럼 다루세요. 새 작업은 `src/`에서 진행하고, 분쟁이 생기면 `handoff/`로 돌아가 검증합니다.
